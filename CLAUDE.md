## Project Overview

Anchor Replay Distillation (ARD) is a data-generation toolkit that builds SFT-ready anchor replay datasets. It samples capability/knowledge anchors from an ontology, asks an input-generator model to write realistic user requests, then asks a target model to produce supervised answers to preserve. The output `anchor_bank.jsonl` can be mixed into fine-tuning datasets for retention across reasoning, writing, translation, coding, tool use, and general knowledge.

ARD is **dataset generation only** — no trainer, model weights, or policy enforcement.

## Configuration

Copy `.env-example` to `.env` and fill in required API values. `.env` is gitignored; never commit it. Runtime settings come from `.env` + CLI flags. The ontology lives at `configs/anchor_ontology.json` with a committed embedding sidecar at `configs/anchor_ontology_embeddings.json`.

Key constraint: do NOT set `max_tokens` by default — leave `ARD_INPUT_GENERATOR_MAX_TOKENS` and `ARD_TARGET_MAX_TOKENS` blank so the provider/model uses its own default output budget.

## Architecture: Two-Hop Pipeline

The core dataflow is:

```
Ontology → Sampler → Anchor Prompts → Input Generator API → Generated Inputs → Target API → Target Answers → Filter → anchor_bank.jsonl
```

### Source layout (`src/ard/`)

| Module | Purpose |
|---|---|
| `cli.py` | CLI parser and all subcommand handlers (`ard anchor-generate`, `ard ontology-embed`, `ard anchor-build-dataset`, `ard eval-forgetting`, etc.) |
| `anchor/__init__.py` | Public API re-exports |
| `anchor/ontology.py` | Loads the single `anchor_ontology.json`, flattens dict/lists into leaf entries with paths. Produces `AnchorOntology` with five sections: languages, knowledge, language_features, capabilities, conversation_types. |
| `anchor/sampler.py` | Generates `AnchorPrompt` objects from ontology. Three strategies: `farthest` (cosine farthest-point sampling over precomputed embeddings of knowledge domains), `balanced` (least-used across all dimensions), `random`. Builds the textual prompt that instructs the input-generator model. |
| `anchor/embeddings.py` | Manages ontology embedding sidecars. Supports local (`sentence-transformers`), API (OpenAI-compatible embeddings endpoint), and hash (lexical bootstrap) backends. Validates `ontology_sha256` to detect stale sidecars. |
| `anchor/input_generator.py` | Calls the input-generator API to produce realistic user messages from anchor prompts. Parses JSON multi-turn conversations, validates message structure (must start/end with user, must alternate roles). |
| `anchor/target.py` | Calls the target model API to produce supervised answers. Preserves reasoning outputs (`<think>...</think>`). Also has a local HF model backend (`answer_anchor_prompts`). |
| `anchor/api_client.py` | Raw OpenAI-compatible API client using only `urllib`. `chat_completion()` returns content text (input generator). `target_chat_completion()` returns `ChatCompletionResult` with `reasoning_status` tracking (`separate`/`inline`/`only`/`absent`). Env-based config via `chat_api_config_from_env()`. |
| `anchor/bank.py` | Data classes for the pipeline: `AnchorPrompt`, `GeneratedInputAnchor`, `TargetAnswerAnchor`. Filtering (empty/failure/too-short/duplicate), train/eval splitting, JSONL I/O. |
| `anchor/pipeline.py` | End-to-end `build_anchor_dataset_api()` — the central orchestrator. Submits prompts to input-generator pool, then pipelines each completed input to the target-answer pool via `ThreadPoolExecutor` (streaming: target answers start before all inputs finish). Handles batching, exact-count refill, dedup across batches, and filter/validation. |
| `anchor/manifest.py` | Builds the `manifest.json` with distribution counts, stats, and config metadata. |

### Data classes and their roles

- **`AnchorPrompt`** (`bank.py`): single-turn or multi-turn user prompt with metadata, generated by sampler
- **`GeneratedInputAnchor`** (`bank.py`): realistic user messages created by the input-generator API
- **`TargetAnswerAnchor`** (`bank.py`): final output — messages + target_answer + metadata, becomes one line in `anchor_bank.jsonl`
- **`ChatAPIConfig`** / **`EmbeddingAPIConfig`** (`api_client.py`): API endpoint/model/key triplet
- **`ChatCompletionResult`** (`api_client.py`): answer text + reasoning_status enum
- **`Ontology`** / **`AnchorOntology`** (`ontology.py`): flattened leaf lists from the JSON ontology tree
- **`OntologyEmbeddings`** / **`OntologyEmbeddingItem`** (`embeddings.py`): embedding vectors for ontology leaves

### Key design decisions

- **No external HTTP client dependency** — uses `urllib.request` only for API calls
- **ThreadPoolExecutor for concurrency** — two pools (input generator + target) running in streaming fashion; target answers begin as soon as individual input generation completes
- **Reasoning preservation** — `target_chat_completion()` detects `reasoning_content` in API responses and wraps it in `<think>...</think>` tags. If content already contains inline think blocks, they're preserved as-is. Reasoning status is tracked per-row.
- **Farthest sampling** — uses precomputed Qwen embeddings for knowledge domain diversity. The committed sidecar (`configs/anchor_ontology_embeddings.json`) has 1024-dim vectors from `Qwen/Qwen3-Embedding-0.6B`.
- **Exact-count mode** — when `require_exact_count=True`, the pipeline runs multiple batches, refilling until the target count of valid answers is reached (up to `max_batches`). By default, runs a single batch.
- **No max_tokens by default** — the API client omits `max_tokens` from requests unless explicitly set, letting the provider control output length.

### Entry Point

- `ard generate` — the one-shot CLI command. Reads every setting from `.env`, accepts zero CLI arguments, runs the full pipeline, and validates outputs (row counts, no API key leaks, manifest consistency). No `scripts/` wrapper needed.

### Configuration

- `src/ard/config.py` — `ARDConfig` loads all settings from `.env` with validation. This is the single source of truth; no parameters come from CLI flags or other sources.

### Tests

Tests live in `tests/` and run with `pytest`. Key patterns:
- Tests use `tmp_path` fixtures for temporary ontologies and output directories
- API-dependent tests use mock `chat_fn` lambdas instead of real HTTP calls
- `test_anchor.py` covers ontology loading, sampling determinism, farthest/balanced strategies, embedding stale detection, filtering, splitting, manifest
- `test_anchor_two_hop.py` covers the full pipeline with fake chat functions, streaming behavior (target answers start before all inputs finish), exact-count refill, dedup across batches, CLI argument parsing
- `pytest` config sets `pythonpath = ["src"]` and `--basetemp=.pytest_tmp`

## Important Constraints

1. **API keys must never appear in outputs** — `cmd_generate` validates output files for key leaks
2. **Output directory safety** — refuses to write into a non-empty output dir unless `--overwrite-output` is set
3. **Embedding sidecar staleness** — if ontology changes, `farthest` strategy raises an error directing to regenerate with `ard ontology-embed`
4. **No `max_tokens` in default API calls** — per user memory, setting `max_tokens` can cause output truncation with thinking models
